# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

See `PROJECT_BRIEF.md` for full product scope, data model, tech stack, and design direction — read it before making scope decisions. Short version: a mobile app (React Native/Expo) for couples in Zrenjanin, Serbia to browse wedding vendors by category, with an ASP.NET Core Web API + SQL Server backend. Solo internship project; no admin web panel is planned — vendor data is managed directly via Swagger/DB by the developer.

## Repo layout

Two independent projects, no root solution/workspace file tying them together:
- `backend/` — ASP.NET Core Web API (.NET 10)
- `mobile/` — Expo/React Native app (SDK 54)

Each is built and run independently.

## Commands

### Backend (`backend/`)
- `dotnet build` — build
- `dotnet run` — run locally (Swagger UI at `/swagger` in Development)
- `dotnet ef migrations add <Name>` — add a migration after changing a model (requires `dotnet-ef`, already referenced via `Microsoft.EntityFrameworkCore.Tools`)
- `dotnet ef database update` — apply migrations to the local SQL Server instance
- No test project exists yet.

### Mobile (`mobile/`)
- `npm start` / `npx expo start` — start the dev server
- `npm run android` / `npm run ios` / `npm run web` — start targeting a specific platform
- `npm run lint` — `expo lint`
- No test suite exists yet.

## Architecture

**Backend** is a pure JSON API — `AddControllers()` / `MapControllers()` only, no MVC views, no Razor, no admin UI in code. Pattern per controller: `Controllers/*Controller.cs` → `Dtos/<Entity>/*.cs` → `Mappers/<Entity>Mappers.cs` extension methods (`.ToXDto()`, `.ToXFromCreateDTO()`) convert between EF Core models and DTOs. This mirrors the developer's prior "FinShark" project (ASP.NET Core Web API + EF Core + JWT), which is the reference pattern to follow for new controllers/auth.

EF Core is code-first: entities live in `Models/`, changes flow into `Migrations/` via `dotnet ef migrations add`. `Data/ApplicationDbContext.cs` is the single `DbContext`, currently exposing `Vendors`, `Categories`, `Photos`, `VendorUnavailableDates`. Connection string in `appsettings.json` points at a local `SQLEXPRESS` instance with `Trusted_Connection` + `TrustServerCertificate` — dev-only, no secrets there.

`Vendor` and `Category` have full CRUD (`VendorController`, `CategoryController`), and `VendorPhoto`/`VendorUnavailableDate` have `Create`/`Delete` nested on `VendorController`. `User`, `Favorite`, JWT auth, and the mobile-facing screens described in `PROJECT_BRIEF.md` are not yet built.

**Child-entity pattern (`VendorPhoto`, `VendorUnavailableDate`)**: these only ever make sense in the context of one `Vendor` (a `VendorPhoto` has zero meaning without its `VendorId`), so they don't get their own top-level controller or full CRUD. Instead: no standalone `GetAll`/`GetById` (they're read as part of `VendorDto`, not fetched independently) and no `Update` (editing doesn't make sense for either — delete + recreate instead). Just `Create`/`Delete`, nested as extra actions on `VendorController` under routes like `POST/DELETE api/vendor/{vendorId}/photos[/{photoId}]` and `POST/DELETE api/vendor/{vendorId}/dates[/{dateId}]`. `VendorId` always comes from the route parameter, never the request body, so a child row can never be attached to the wrong vendor by mistake — see `VendorMappers.ToVendorPhotoFromCreateDto`/`ToVendorUnavailableDateFromCreateDto`, both of which take `vendorId` as an explicit parameter rather than reading it off the DTO. Both `Create` endpoints guard `vendorId` with `await _context.Vendors.AnyAsync(v => v.Id == vendorId)` before mapping, returning `NotFound("Vendor does not exist")` (done 2026-08-27). It's `NotFound`, not `BadRequest`, because `vendorId` is a route segment — a bogus one means the URL names a vendor that isn't there, matching what `DeletePhoto`/`DeleteUnavailableDate` already return. Before this, a bogus `vendorId` fell through to an FK violation and surfaced as a raw 500.

**Watch for EF Core reference cycles when embedding a child entity in a parent DTO.** `Vendor` has `List<VendorPhoto> Photos` and `List<VendorUnavailableDate> UnavailableDates`; both child models have a `Vendor` back-reference. When a query does `.Include(v => v.Photos)` (or `.Include(v => v.UnavailableDates)`), EF's relationship fixup sets both directions, so the raw object graph is a cycle (`Vendor → Photos → VendorPhoto → Vendor → ...`). Confirmed this actually throws `System.Text.Json.JsonException: A possible object cycle was detected` at runtime (not a compile error) the first time a vendor had ≥1 photo. Fix is to never put the raw EF model in a DTO — `VendorDto.Photos`/`VendorDto.UnavailableDates` are `List<VendorPhotoDto>`/`List<VendorUnavailableDateDto>` (plain DTOs with no back-reference), mapped via `VendorMappers.ToVendorPhotoDto()`/`ToVendorUnavailableDateDto()`. Apply the same fix for any future child entity added to `VendorDto`.

**Vendor photos are URLs, not uploaded files.** `CreateVendorPhotoDto.ImageUrl` is a plain string — Swagger/the API never receives file bytes. Planned approach: upload images to Cloudinary's free tier (generous enough for this project's scale — dev pastes the resulting URL into `ImageUrl`), rather than running a self-hosted file server. Not yet implemented or decided in code; revisit if/when actual photo upload UX is built. **Data state (2026-08-26): the `Photos` table was completely empty until now** — which is the reason every vendor card and vendor hero in the mobile app renders the gradient placeholder rather than a photo; it was the data, not a bug in the fallback. Two throwaway rows now exist on vendor 8 (`Kovač Residence`), `sortOrder` 0 and 1, both pointing at `picsum.photos/200` — the dev added them purely to exercise the `SortOrder` fix and intends to delete them. Note `picsum.photos/200` returns a *random* 200px image per request, so it can't actually confirm which photo sorted first and is too small for the 230dp hero; fixed ids at a real size (`picsum.photos/id/10/800/600`) are the better throwaway if this is redone.

**Category names are English in the DB, pending a Serbian rename (open 2026-08-18).** The eight `Categories` rows are still `Venue`/`Band`/`Photographer`/`Hair & Makeup`/`Jewelry`/`Wedding Dress`/`Decoration`/`Cakes` (ids 1–7 and 9). The agreed Serbian names, taken from `visual-direction-mockup.html`, are **Sale / Bendovi / Fotografi / Frizura i šminka / Nakit / Venčanice / Dekoracija / Torte** — the dev is doing this themselves through Swagger `PUT api/category/{id}`, deliberately going through their own endpoint rather than raw SQL. `Torte` for Cakes is unconfirmed (`Poslastičarnice` is the alternative — shop rather than product). **Filter vendors by category server-side (done 2026-08-11).** `VendorController.GetAll` takes `[FromQuery] int? categoryId`; when supplied it adds `.Where(v => v.CategoryId == categoryId.Value)` (translated to SQL, so the DB filters), else returns all — nothing that called `GET /vendor` before breaks. The mobile Category-list screen calls `GET /vendor?categoryId={id}` rather than fetching all vendors and filtering client-side. **Decision rationale (settled after a long back-and-forth, worth not re-litigating):** at realistic scale (~20 vendors total in Zrenjanin, ~100/category as an "impossible" ceiling) client-side filtering would be *plenty* fast — the `.filter()` itself is a non-issue until ~10k items. The real reason to go server-side is the *initial payload*: client-side needs to download every category's vendors (with embedded photos/dates) just to show one, and per-category fetch avoids that at scale. It's also more future-proof than reformatting both projects later. Responsiveness caveat that drove the choice: the mentor disliked another app (vencaj.me) lagging ~2s on filters — that lag was a **backend round-trip on every filter tap**. Our `?categoryId=` fires **once, on screen navigation** (not per interaction), so it doesn't reproduce that. **Rule going forward:** fetch a category server-side on navigation, but any *in-screen* filter/sort applied to the already-loaded list (e.g. sort by capacity, filter by city) must be **client-side** — never round-trip per toggle. General principle landed on: server-side when the set is big or paged; client-side when it's already small and loaded.

**Repository pattern / QueryObject deliberately deferred (2026-08-11).** The mentor (who steered FinShark and BulkyBook to a repository layer) argues for repositories here too: fat controllers, DB calls in controllers, enforced abstraction, single-point-of-change. Those principles are sound, but **not adopted for this project yet** because: EF's `DbContext`/`DbSet` is already a repository + unit-of-work, so a layer on top is often a pass-through; the strongest pro (mockable-for-tests) is unused since there's **no test project**; and the codebase is consistently thin-controller CRUD with almost no business logic (`Favorite.choose` is the only real logic). The one concrete win the mentor's argument had on real code — the `.Include(Category/Photos/UnavailableDates)` chain duplicated across four `VendorController` actions — was fixed the lightweight way instead: an `IQueryable<Vendor>` **extension method** `WithDetails()` in `backend/Helpers/VendorQueries.cs` (a separate Helpers folder, not a private controller method — the dev's call, and the cleaner one). All four actions now read `_context.Vendors.WithDetails()...`. QueryObject is *premature* — it earns its place with multi-param filter/sort/pagination endpoints, and since most filtering is going client-side, that backend surface deliberately won't grow. **The full repository pattern is a legitimate post-MVP pass** (the mentor teaches it and the code is meant to look professional for the commercial angle) — but do it *after* the MVP screens work, across *all* controllers at once (not Vendor-only, or the codebase splits), not as a mid-build detour.

**User/auth (done).** Using ASP.NET Core Identity (`IdentityUser`/`IdentityDbContext`/`UserManager`/`SignInManager`), not a hand-rolled `User` model + custom password hasher — the app is headed toward being sold commercially (developer + their mentor plan to partner and charge for access, separate from any in-app purchase), so Identity's built-in roles and account lockout are worth the extra setup vs. rolling it by hand. Note `PasswordHasher<T>` and the JWT-handling libraries (`System.IdentityModel.Tokens.Jwt`, pulled in transitively via `Microsoft.AspNetCore.Authentication.JwtBearer`) are identical either way — Identity isn't "safer crypto," it's more built-in scaffolding (roles, lockout) around the same primitives. Packages added so far: `Microsoft.AspNetCore.Identity.EntityFrameworkCore`, `Microsoft.AspNetCore.Authentication.JwtBearer`.

`AppUser : IdentityUser` (`backend/Models/AppUser.cs`) is done — adds `CreatedAt`, `YourName`, `YourPartnerName`, `WeddingDate`. All three are non-nullable: name/partner-name/wedding-date are collected as required fields at registration (not an optional editable-later step), specifically so the mobile app never needs two different UI states depending on whether profile data exists yet. `WeddingDate` is `DateOnly`, matching `VendorUnavailableDate.Date` — a wedding date has no meaningful time component, so `DateTime` would be the wrong type here.

No `Role` column on `AppUser`. An eventual "Admin" designation is needed — not for any admin UI (none is planned, per `PROJECT_BRIEF.md`) but to lock down `Vendor`/`Category` write endpoints once this is deployed publicly (they currently have no `[Authorize]` at all, which is fine only while nothing is reachable but `localhost`). That'll use Identity's own `RoleManager<IdentityRole>` / `AspNetUserRoles` join table, assigned to the developer's one account, rather than a plain string field on `AppUser`.

`AccountController` (`Register`/`Login`) is done, see build-order item 5 below.

**Favorite (done).** `Favorite` (`backend/Models/Favorite.cs`) is a plain join entity — `Id`, `UserId` (string, `AppUser.Id`), `User` nav, `VendorId`, `Vendor` nav; no `CreatedAt`, deliberately left off since `Id` already sorts chronologically and nothing in scope needs a real timestamp. `ApplicationDbContext` overrides `OnModelCreating` (the first override it needed) to add a unique index on `(UserId, VendorId)` via `modelBuilder.Entity<Favorite>().HasIndex(f => new { f.UserId, f.VendorId }).IsUnique()`, calling `base.OnModelCreating` first since `IdentityDbContext` needs that to configure its own tables. `FavoriteDto` is intentionally flat (`Id`, `VendorId`, `VendorName`) rather than embedding a nested `VendorDto` — the favorites list only needs enough to link back to a vendor detail screen. `FavoriteController` is the first controller with `[Authorize]` on it (all others are still open, per the build-order rationale above); `UserId` always comes from the JWT via `User.FindFirstValue(ClaimTypes.NameIdentifier)`, never a route param or body, matching the "can't attach to the wrong owner" pattern already used for `VendorId` on child entities. `Add`/`Remove` take only `[FromRoute] int vendorId` — no `CreateFavoriteDto` exists because there's no additional data a client could legitimately send (`UserId` from the token, `VendorId` from the route already cover it). `Add` double-checks for an existing `(UserId, VendorId)` row with `.Any()` before inserting (returns a clean `400` instead of letting the unique index throw a raw `DbUpdateException`), while `Remove` uses `.FirstOrDefault()` on the same compound condition to get the actual row to delete.

**Swagger's JWT bearer setup has a sharp edge worth remembering.** The obvious/commonly-documented way to wire up `AddSecurityDefinition`/`AddSecurityRequirement` for JWT bearer auth (per pre-.NET 10 Swashbuckle examples) uses `Microsoft.OpenApi.Models.*` types and `Type = SecuritySchemeType.ApiKey`. Neither works with this project's actual stack (`Swashbuckle.AspNetCore` 10.2.3 pulling in `Microsoft.OpenApi` 2.x for .NET 10): (1) `Microsoft.OpenApi` v2 dropped the `.Models` sub-namespace entirely — types now live directly under `Microsoft.OpenApi` — and replaced `OpenApiSecurityScheme.Reference` with a separate `OpenApiSecuritySchemeReference` type, and `SwaggerGenOptions.AddSecurityRequirement` now expects a `Func<OpenApiDocument, OpenApiSecurityRequirement>` instead of a bare object, so a reference can resolve against the document being built. (2) Even once it compiles, `Type = SecuritySchemeType.ApiKey` silently sends whatever's typed into the Swagger UI "Authorize" box verbatim into the `Authorization` header — it does **not** prepend `Bearer `, regardless of `Scheme = "Bearer"` being set. That produced a confirmed-firsthand `401` on every `[Authorize]`d endpoint (first hit while testing `Favorite`, since it was the first protected controller) even with a correct token, because the header was `Authorization: <token>` with no scheme prefix. Fix was `Type = SecuritySchemeType.Http` with `Scheme = "bearer"` — that combination is what makes Swagger UI actually add the `Bearer ` prefix for you. See the working config in `Program.cs`.

Built as `FavoriteController.ChosenWeddingVendorSelect`. The earlier open question is resolved the auto-create way: if no `(UserId, VendorId)` `Favorite` row exists yet, `choose` creates one on the spot, so choosing directly from a vendor profile just works without a prior `Add` — it 404s first if the `vendorId` doesn't match a real `Vendor`.

## Where we left off (backend build order)

Working controller-by-controller through the API before touching the mobile app is a deliberate choice, not just habit: `Vendor`/`Category`/`Photo`/`UnavailableDate` are all public, admin-managed, read-mostly data that needs no `[Authorize]` at all, so auth can slot in once, right before `Favorite` (the only user-owned resource), instead of being retrofitted onto every controller.

Order, and current status:
1. ✅ `Category` — full CRUD
2. ✅ `Vendor` — full CRUD
3. ✅ `VendorPhoto` — `Create`/`Delete` nested on `VendorController`, embedded read via `VendorDto.Photos`
4. ✅ `VendorUnavailableDate` — same pattern as `VendorPhoto`, `Create`/`Delete` nested on `VendorController`, embedded read via `VendorDto.UnavailableDates`
5. ✅ `User` model + JWT auth. Modeled loosely on the developer's prior "FinShark" project, but using ASP.NET Core Identity rather than FinShark's approach (see User/auth note above). Packages installed, `AppUser` model written, `ApplicationDbContext` converted to `IdentityDbContext<AppUser>`, `AddIdentity<AppUser, IdentityRole>().AddEntityFrameworkStores<ApplicationDbContext>().AddDefaultTokenProviders()` registered in `Program.cs`, `app.UseAuthentication()`/`app.UseAuthorization()` added to the pipeline (in that order, between `UseHttpsRedirection` and `MapControllers`), migration added and applied to the DB, JWT `Issuer`/`Audience`/`SigningKey` added to `appsettings.json`. `AddAuthentication(options => { DefaultAuthenticateScheme = DefaultChallengeScheme = JwtBearerDefaults.AuthenticationScheme }).AddJwtBearer(...)` wired in `Program.cs` (overrides the cookie scheme `AddIdentity` defaults to), validating issuer/audience/signing key out of config. `ITokenService`/`TokenService` (`backend/Interfaces/ITokenService.cs`, `backend/Services/TokenService.cs`) builds a `SymmetricSecurityKey` once in the constructor, `CreateToken(AppUser)` embeds `ClaimTypes.NameIdentifier`/`ClaimTypes.Email` claims, signs with `HmacSha256Signature` (switched from the initially-planned `HmacSha512Signature` — hit `IDX10720` at runtime because the original `SigningKey` was only 128 bits and HMAC-SHA512 needs ≥512; rather than lengthen the key indefinitely, dropped to SHA-256's 256-bit minimum and generated a 64-byte `openssl rand -base64 64` key, well above either threshold), expires 7 days out via `DateTime.UtcNow` (not `.Now` — avoids server-timezone bugs once deployed). `RegisterDto`/`LoginDto`/`NewUserDto` under `backend/Dtos/Account/` — `NewUserDto` (`Email`, `YourName`, `Token`) is the shared response shape returned by both actions. `AccountController` (`backend/Controllers/AccountController.cs`) is built and manually verified against all three cases (successful register+login, duplicate-email register → `400`, wrong-password login → `401`): `Register` builds an `AppUser` from `RegisterDto`, calls `UserManager.CreateAsync`, and — deliberately, to skip a redundant immediate re-login — returns a JWT right away on success (auto-login), matching FinShark's confirmed-safe-enough-pre-launch pattern; email confirmation was considered and explicitly deferred (needs a real email provider plus a publicly reachable confirmation URL, neither of which exist while the API is `localhost`-only — revisit alongside deployment). `Login` looks the user up via `UserManager.FindByEmailAsync` (uses Identity's normalized-email column, unlike FinShark's raw `Users.FirstOrDefaultAsync` — case-insensitive lookup for free) then `CheckPasswordAsync`, returning the identical `Unauthorized("Invalid email or password.")` message whether the email doesn't exist or the password is wrong, so the response can't be used to enumerate registered emails. Both actions wrap their body in `try`/`catch`, returning `StatusCode(500, e.Message)` for unexpected failures and `BadRequest`/`Unauthorized` for expected ones (bad `ModelState`, failed `IdentityResult`, bad credentials). Note: `CreateAsync` and `CreateToken` aren't in one transaction — confirmed firsthand that if something after a successful `CreateAsync` throws (e.g. the earlier signing-key bug), the user row is already committed even though the client sees a `500`; harmless today since `CreateToken` is pure in-memory and won't realistically throw once config is valid, but worth remembering if `Register` ever grows another post-`CreateAsync` step.

- ✅ **Async everything — DONE 2026-08-26**, now across **all three controllers**: `VendorController` (nine actions), then `CategoryController` (five) and `FavoriteController` (four), so no one-controller-out-of-three split remains. `ToListAsync`/`FirstOrDefaultAsync`/`SaveChangesAsync`, actions are `async Task<IActionResult>`. **Order matters** — `await query.ToListAsync()` *then* `.Select(v => v.ToVendorDto())`; the mappers are plain C# and are not SQL-translatable, so the materialize-then-map shape must be preserved. Two points worth keeping, both of which came up while doing it: (1) **only the terminal call goes async.** `WithDetails()`, `.Where()`, `.Include()` build an `IQueryable` and hit the DB zero times, so they stay sync — the `await` belongs solely on the operator that executes SQL. Coming from FinShark this looks like something's missing, but the repository's `GetAllAsync` body was only ever `return await stocks.ToListAsync();` — with no repository that one line just lives in the controller. (2) **`AddAsync` is not the async form of `Add`** — it returns a completed task, does no I/O, and exists only for value generators needing a DB round-trip for the key (SQL Server HiLo). Identity columns don't. Use plain `Add`; only `SaveChangesAsync` is awaited. `AddAsync` was written first here and reverted. (3) **Two mistakes hit while converting the list actions, both worth recognising on sight.** First, `await _context.Categories.ToListAsync().Select(c => c.ToCategoryDto())` doesn't compile: `await` binds looser than `.`, so C# parses it as `await (ToListAsync().Select(…))` and `Task<List<T>>` has no `Select`. Second, the fix-attempt `categories.Select(c => c.ToCategoryDto());` on its own line silently does nothing — `Select` returns a *new lazy* sequence rather than mutating `categories`, so discarding it means the mapper never runs and `Ok(categories)` ships raw EF models instead of DTOs. Only the second one is dangerous, since it builds clean. The shape that works is two statements: `var x = await …ToListAsync();` then `var xDtos = x.Select(…);` and return `xDtos`.

### Backend — `FavoriteController.ChosenWeddingVendorSelect` restructure

✅ **DONE 2026-08-26.** The old shape queried `target` *before* the vendor-exists check, and its auto-create path called `SaveChanges()` then **re-queried with `Include`** purely to reach `Vendor.CategoryId` — two `SaveChanges` calls, not in a transaction. Now one pass: load the **`Vendor`** first (that single query is both the existence check and the source of `CategoryId`), find-or-create the `Favorite` **without saving**, flip the siblings, then a single `SaveChangesAsync()`. `.Include(f => f.Vendor)` is gone from the `siblings` query — filtering on `f.Vendor.CategoryId` translates to a JOIN on its own, so the `Include` only materialized objects that got thrown away.

**Two things that only became clear by running it, and are worth not re-deriving:**
- **Loading the `Vendor` first is what kills the re-query.** The re-query existed solely because a freshly-`new`ed `Favorite` has no `.Vendor` navigation, and the old sibling filter read `target.Vendor.CategoryId`. Once `vendor` is a local, that line becomes `vendor.CategoryId` and the whole reload disappears. A halfway version — dropping the `SaveChanges` but keeping the re-query — is **worse than either**: it queries for a row that hasn't been inserted yet, gets `null` back, and NREs a few lines down. It compiles clean.
- **`FavoriteMapper.ToFavoriteDto` dereferences `favorite.Vendor.Name`/`.CategoryId`, and it still works with no `Include` anywhere** — because `vendor` was loaded into the same tracked context at the top, EF **relationship fixup** wires `target.Vendor` to that instance, on both the found and the brand-new-`Add`ed path. Verified, not assumed: choosing a vendor with no prior favorite returns a populated `vendorName`/`categoryId`. **This is load-bearing but implicit** — if anyone ever adds `AsNoTracking()` to either query here, or reorders so the `Vendor` load happens after the mapper call, the DTO starts NREing with nothing in the code explaining why.

**Verified end-to-end 2026-08-26** against `dotnet run --launch-profile http` with a throwaway account, all five cases passing: auto-create with no prior favorite (200, nav populated), sibling flip in the same category (the previous pick goes `false`), bogus vendor id (404), choose on an already-existing favorite (reuses the row — the `id` doesn't change, no duplicate insert), and cross-category isolation (choosing a band leaves the venue pick alone). The EF SQL log confirms the single-save design: choosing a vendor that also displaces a sibling emits **one batch** containing the `UPDATE` and the `INSERT` together, not two round-trips.

Separately, `Add`'s `.Any()`-then-insert is a TOCTOU race — two concurrent requests can both pass the check, and the unique index then turns the loser into a raw `DbUpdateException`/500 instead of the clean 400. Acceptable for MVP (single user, no real concurrency), recorded so it isn't a surprise later.

## Working style

Per `PROJECT_BRIEF.md`: this is a learning project for a 2nd-year student who is comfortable with C#/EF/ASP.NET/React but new to React Native/Expo. Prefer small incremental steps with explanations over large generated features, especially for anything React Native/mobile-specific. If a request would reintroduce something explicitly listed as out-of-scope in `PROJECT_BRIEF.md` (booking, payments, in-app messaging, admin panel, vendor self-service, reviews), flag it rather than building it.

Default to explaining what to write and letting the developer type it themselves, checking/reviewing after (mirrors how `Category` and `VendorPhoto` CRUD got built) — write code directly only when they explicitly ask for it (e.g. "write it for me," "I'm confused, just do it"). **Note "help me" ≠ "write it"**: asked to help with a half-written function, point at the specific broken lines and let them fix each one; writing the whole file was rejected mid-write on 2026-08-18.

**The same rule covers data and environment, not just code.** DB writes, seeds, migrations and config edits are the dev's to run — say what needs to change and hand over the exact statements (or the Swagger call), don't execute it. Reading the DB to check current state is fine; it's writes that need the ask. Confirmed 2026-08-18: Claude ran `sqlcmd` UPDATEs to rename the categories and the dev pushed back — "i wanted to check myself but you did it auto" — then reverted them to redo it through Swagger. When something might have a subtle runtime bug (not just a compile error) — e.g. the EF cycle above — actually run the app and hit the endpoint rather than reasoning about it in the abstract.
